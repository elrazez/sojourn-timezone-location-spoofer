# Sojourn's own New Tab Page

Sojourn declares `chrome_url_overrides.newtab` pointing at `newtab.html`, a blank extension page with a title, a `color-scheme` meta and nothing else, so every new tab shows a page Sojourn may attach to from the moment the tab exists. Chrome refuses `chrome.debugger.attach` while `chrome://new-tab-page` is committed, and an extension may attach to its own `chrome-extension://` pages (the attach check refuses only another extension's, `docs/research/chrome-debugger-api.md` section 1), so the tab is attached at `tabs.onCreated`, before anything commits, and Blink replays the zone into the next document by itself. That replay is why the site the user goes to next observes the Override in its first script without Sojourn sending anything new.

This closes the largest Residual Trace phase 06 measured: 20 misses in 20 loads leaving the New Tab Page, on the most common way a person opens a site.

## Considered Options

- **A blank New Tab Page of Sojourn's own (chosen).** One manifest key, one file with no script in it, no new permission, and no new protocol method. It closes the gap before the navigation starts rather than racing it.
- **The `webNavigation` permission (rejected).** `onBeforeNavigate` reaches the service worker earlier than `tabs.onCreated` does, so the attach would land sooner, but it still lands after the request for a document the browser already holds, so the cached case keeps missing. The permission also adds a browsing-history line to the install prompt, which ADR-0002 refuses for a partial fix.
- **A reload after a late attach (rejected).** By the time the attach lands the first document has run its scripts, so nothing is unsent: a script that already read the real zone keeps what it read, and the reload would hide the miss from the Audit while making every such tab load twice.
- **Accepting the gap (rejected).** It is measurable, it is the biggest one, and it sits where people start.

## Consequences

- The user's New Tab Page becomes Sojourn's blank page: no search box, no shortcuts, no most-visited tiles. Chrome focuses the omnibox on an extension New Tab Page, so typing a url works exactly as it did.
- The install prompt says so: Chrome tells the user the extension changed the page shown on new tabs and offers to keep or restore it. That line is the price of this decision and belongs in the README beside the debugger bar.
- The manifest gains one key beyond the two permissions, and only this one. ADR-0002's boundary is otherwise unchanged: no content script, no web accessible resource, no host permission, no network request, and the page carries no script, no stylesheet and no inline style.
- **A tab showing this page is Sealed.** Chrome keeps the tab's url at `chrome://newtab/` while the extension page is the document, so `attach`, `detach` and every `sendCommand` about that tab answer `Cannot access a chrome:// URL`. The session that landed at `tabs.onCreated` stands and the page observes the Override, which is why the tab is Covered, but Sojourn cannot say another word to it until it goes somewhere. Three things follow:
  - The attach and the first zone send both have to beat the commit, and the window is about 15 ms, so a new tab cannot wait behind the service worker's queue: measured, a tab that waited 0 to 2 ms was Covered and one that waited 5 ms or more never was. Coverage runs a new tab's cycle off that queue for this reason alone.
  - A tab already showing the New Tab Page when Sojourn starts covering, which is a browser start or a first Selection with a new tab open, cannot be attached at all. It reads Restricted and the site it goes to next observes the real zone in its first script, which phase 06.1 asserts as a test of its own. The New Tab Page narrows the gap to that case rather than removing it.
  - Disabling cannot reach a Sealed tab either, so Sojourn re-issues the detach until the tab leaves the New Tab Page. The one document that navigation lands on still observes the Override in its first script, because Chrome replays into it the session Sojourn has not been allowed to give up, and the next tick hands the real zone back. Phase 06.1 asserts both halves. Reporting a refused detach as a detach is what used to make it permanent, and the same refusal reaches a City change one document late on such a tab.
- **Incognito is the one carve-out this key cannot reach.** Chrome refuses a New Tab Page override in an off-the-record profile for every extension, split mode or not, by an explicit term in the condition, `url.host() != chrome::kChromeUINewTabHost` (`chrome/browser/extensions/extension_url_overrides.cc` 402-413, read at tag `154.0.8037.17`, and the reference page says the same in one line, "In incognito windows, extensions can't override New Tab pages": `docs/research/keeping-the-new-tab-page.md` section 5). So an incognito new tab is Chrome's own page, which was never attachable, and the site typed into it observes the real zone in its first script, which is the 0 of 10 that file's section 2 measured for the stock page. Source-derived, not measured inside incognito, and named in the brief's Residual Traces and in the README.
- The gap that remains for a tab created straight onto a url is narrower and named in the brief: a bookmark or another application, where the document comes from the browser's cache and no request ever reaches the network. Phase 06 measured 10 misses in 10 such tabs with 0 server requests, and phase 06.1 measured it again after this change.
